## 1组

Q1：图像数据是怎么管理的 

A:

1. 存储：图像文件存本地磁盘 / 服务器共享文件夹；数据库只存图像路径、文件名、采集时间、产品条码、缺陷结果等元数据。
2. 命名规则：一般用 条码_时间戳_相机编号.bmp，保证唯一。
3. 归档策略：按天 / 按产品型号分文件夹；设置自动清理，保留最近 N 天图片，防止磁盘占满。
4. 内存管理：采集图像用完及时释放（Halcon/VP 图像资源 Dispose），不长期缓存原图；预览只用缩略图。
5. 索引：数据库记录绑定产品 ID，方便追溯时快速找到对应图片。

Q2：产线上，数据库插入，每秒钟会插入多少条数据？

 A:

1. 普通单相机视觉工位：每秒1~5条检测记录，一条记录对应一个产品检测结果。
2. 高速线扫、多相机并行场景：最高可达10~30条/秒。
3. 落库方案：不会单条循环Insert，采用内存队列异步缓存+批量BulkCopy写入，避免数据库IO阻塞视觉检测流程。

Q3：表结构是怎么设计的 

A:

1. 产品信息表：产品型号、版本、上下限公差、检测方案ID。
2. 检测结果主表：主键ID、条码、产品ID、检测时间、OK/NG、相机编号、图像路径、操作员，一条产品检测对应一行。
3. 缺陷子表：缺陷ID、关联主表ID、缺陷类型、缺陷坐标、置信度、缺陷图片路径；一个产品多个缺陷，对应多条记录。
4. 系统日志表：软件日志、通讯异常、设备报警记录。
5. 主键选用雪花ID或自增ID；查询关键字段建立索引。

Q4：新增数据后要查询，查询的时候使用什么策略，保证软件不卡并且查的快 

A:

1. 索引优化：给常用查询字段建立索引，如条码、时间、产品型号；不对所有字段建索引，防止降低插入性能。
2. SQL写法：禁止select *，只查询业务需要的字段。
3. 分页+条件过滤：前端分页加载，单次限制返回行数；查询增加时间范围、条码等条件缩小数据集。
4. 缓存策略：高频重复查询增加内存缓存，减少数据库访问。
5. 分表归档：大数据量场景按月份分表，历史冷数据迁移归档。
6. 异步执行：查询逻辑放在异步Task执行，不阻塞Winform UI线程。

Q5：全流程数据追溯

 A:

1. 来料扫码绑定产品SN，上线、视觉检测、缺陷信息、图像路径、设备参数、操作员、时间全部关联该SN。
2. 追溯查询：输入SN，可一次性调出全工位检测记录、缺陷列表、缺陷原图、设备报警日志。
3. 报表统计：支持按时间段、OK/NG、缺陷类型做良率统计并导出Excel报表。
4. 数据留存：按客户要求保存3个月~2年，到期自动清理图片文件，数据库元数据保留。

Q6：串口方面的对接，简单表述对接过哪些设备 

A:

1. 对接设备：称重仪表、编码器、激光测距传感器、温控模块、读码器、支持Modbus RTU的PLC。
2. 通信协议：自定义ASCII协议、Modbus RTU协议。
3. 开发要点：串口单独线程读写，增加锁机制，防止并发冲突。

Q7：遇到对方设备扯皮，比如断联、数据交互不上，怎么排查和解决问题 

A:

1. 硬件层：SSCOM串口工具直接收发报文；检查接线、屏蔽接地、终端电阻，确认波特率、数据位、校验位、停止位。
2. 协议层：抓取原始报文，核对帧头、帧尾、CRC校验、字节序，确认协议文档一致性。
3. 问题定位：SSCOM能正常收发，就是我方软件代码问题；SSCOM也无法通信，保存报文日志，给到设备厂商确认。
4. 代码优化：增加心跳包、超时重发、串口读写加锁、异常自动重连，处理粘包分包问题。

Q8：模板匹配的原理 

A:

1. NCC灰度归一化相关匹配：对比图像灰度信息，有一定光照适应性，对旋转、缩放敏感。
2. 形状匹配：提取模板边缘轮廓，只比较几何形状；抗光照变化能力强，支持一定角度旋转，计算量更大。
3. 执行流程：采集制作模板、提取特征、在ROI区域遍历计算相似度；设置相似度阈值，超过阈值判定找到目标，输出坐标。
4. 性能优化：缩小ROI搜索范围，减少计算耗时。

## 2组

Q1：visionPro中用的工具有哪些？

 A:

1. 定位类：CogPMAlignTool（PatMax模板匹配）、CogFindCircleTool找圆、CogFindLineTool找线。
2. 测量类：Cog CaliperTool卡尺、CogDistanceTool距离测量、CogAngleTool角度测量。
3. 缺陷检测类：CogBlobTool斑点分析、CogHistogramTool灰度分析。
4. 图像预处理：CogImageConvertTool图像转换、CogFilterTool滤波、CogContrastTool对比度调整。
5. 脚本类：CogScriptTool简单脚本、CogAdvancedScriptTool高级脚本。
6. 其他：CogBarcodeTool读码、CogCalibNPointToNPointTool标定工具。

Q2：是传统算法还是深度学习相结合？

 A:

1. 项目里以VisionPro传统机器视觉算法为主，PatMax、Blob、卡尺、模板匹配这类传统工具稳定性高，适合尺寸测量、定位、简单缺陷。
2. 遇到模糊划痕、低对比度微小瑕疵、复杂纹理缺陷，传统算法很难区分缺陷与纹理，会引入深度学习算法做辅助检测。
3. 两者结合：传统算法做产品定位、ROI裁剪，将裁剪后的图像送入深度学习模型做缺陷分类与分割，兼顾速度与检测效果。

Q3：visionPro中用的工具PMA中的参数：角度，是相对于什么的角度？是相对于输入空间的还是相对于什么的？ 

A:

1. PMA（CogPMAlignTool）输出角度，是**相对于训练模板图像坐标系**的旋转角度。
2. 不是输入图像空间，模板训练时的方向作为0度基准。
3. 当目标物体顺时针旋转，角度为负值；逆时针旋转，角度为正值。
4. 可配合标定，把这个角度转换到世界物理坐标系。

Q4：visionPro中用的工具PMA，在使用时如何提升性能和运行速度？

 A:

1. 缩小搜索ROI：定位前先用传感器或者粗略定位，限定PatMax搜索区域，减少图像遍历范围。
2. 控制角度范围：只设置物体实际会出现的旋转角度区间，关闭不必要的大角度搜索。
3. 降低金字塔层级：适当减少金字塔层数，层数越少速度越快，但要平衡稳定性。
4. 模板优化：模板只保留关键边缘特征，剔除无关背景；模板尺寸不要过大。
5. 图像预处理：提前做降噪，减少无效特征；降低图像分辨率（在精度允许前提下）。
6. 并行处理：上位机多线程采集图像，PMA运算和图像采集异步执行。

Q5：你认为对于瑕疵检测最重要的是什么？

 A:

1. 稳定的成像：光源、镜头、相机选型，保证缺陷和背景之间有足够对比度，这是基础。
2. 明确缺陷标准：和客户对齐OK/NG样件，建立缺陷判定标准，避免边界样件争议。
3. 算法鲁棒性：能抵抗光照波动、产品轻微形变、位置偏移，降低误检、漏检。
4. 合理的阈值：平衡漏检率和误检率，满足客户的良率要求。
5. 节拍性能：算法执行时间满足产线生产节拍。

Q6：那如果就是你的检测项目达不到客户要求的检测节拍，你会从哪些方面去进行优化呢？

 A:

1. 算法层面：缩小工具ROI，限制PMA角度范围；精简工具数量，去掉不必要的图像预处理；合理调整图像金字塔。
2. 图像层面：在精度允许条件下降低相机分辨率，减少单帧图像数据量。
3. 软件框架：把图像采集、算法运算、UI显示拆分成独立异步线程，避免UI阻塞算法；使用内存池复用图像，减少内存频繁申请释放。
4. 硬件层面：升级CPU，使用多核分担运算压力；更换高速相机，降低图像传输耗时。
5. 业务逻辑优化：非必要图像不保存，数据库异步落库，不要在算法主线程执行IO操作。

Q7：visionPro中的工具：找线工具，的对比度阈值含义是什么？

 A:

1. 对比度阈值代表边缘两侧灰度差值的最小值。
2. 工具在扫描剖面时，只有边缘明暗灰度差大于这个阈值，才会被判定为有效边缘。
3. 阈值设置偏大：会过滤掉微弱、低对比度边缘，可能丢失真实边缘。
4. 阈值设置偏小：容易把噪声、轻微灰度波动识别成边缘，造成误检出多条线。

Q8：说一下工作经验，曾经做过的项目，这个项目做了什么遇到了哪些“问题”，以及怎么解决的？

 A:

1. 项目简介：基于C# Winform+VisionPro开发的产品外观与尺寸检测上位机。相机采集产品图像，PatMax定位，卡尺、Blob完成尺寸测量与缺陷检测，数据存入数据库，实现产品追溯。
2. 遇到问题1：产品位置偏移+光照变化，模板匹配偶尔定位失败。
3. 解决：优化光源，增加漫射照明；合理设置PMA角度、缩放范围，调整金字塔层数，提升定位稳定性。
4. 遇到问题2：产线节拍紧张，图像采集+算法总耗时超标。
5. 解决：拆分多异步线程；缩小各工具ROI；图像保存、数据库写入放到后台队列异步执行。
6. 遇到问题3：串口和PLC通讯偶发断连，交互不稳定。
7. 解决：串口单独线程读写，增加心跳包、超时重连，报文增加CRC校验，处理粘包分包问题。

Q9：阐述一下如何确定硬件选型。

 A:

1. 确认检测需求：检测精度、视场大小、产线节拍、缺陷类型。
2. 相机选型：由视场、精度计算所需像素；根据产线速度选择合适帧率；考虑全局快门/卷帘快门。运动物体优先全局快门。
3. 镜头选型：根据工作距离、视野、相机靶面选焦距；检测微小缺陷选用远心镜头消除透视畸变。
4. 光源选型：依据缺陷表面材质、缺陷类型，选择环形、同轴、条形光源，目标是最大化缺陷与背景对比度。
5. 辅助硬件：根据通讯需求选择IO卡、串口/网口模块；CPU选型要预留算法算力余量。
6. 样件打光测试：拿到客户样件做打光试验，验证成像效果，最后敲定整套硬件。

Q10：整体框架是已有的，还是自己写的？

 A:

1. 整体上位机框架是基于C# Winform自主开发。
2. 底层封装VisionPro工具调用、图像采集、数据库操作、串口/TCP通信模块。
3. 预留配置界面，方便现场修改检测参数；支持方案加载保存、日志记录、数据追溯。
4. 部分通用组件可以复用之前项目封装好的类库，核心业务逻辑按项目需求开发。

Q11：通信模块是自己写还是有现成的框架？

 A:

1. 串口（RS232/485）：使用C#自带SerialPort类自行封装通信类，做报文收发、校验、重连机制。
2. TCP客户端/服务端：可以基于Socket自己封装，也可以使用成熟开源通信框架。
3. Modbus：可以手写Modbus RTU报文解析，也可以引用现成Modbus库。
4. 所有通信模块都会统一封装，提供事件回调给上层UI，方便统一处理收发数据、异常断连。

Q12：自定义编程界面有问题吗？ 

A:

1. VisionPro自带QuickBuild快速搭建调试界面，但灵活性差，不适合产线交付。
2. 实际项目一般用C# Winform/WPF自定义上位机界面。
3. 自定义界面优势：自由布局、权限管理、数据报表、追溯查询、日志系统，适配客户操作习惯。
4. 需要注意：图像渲染、算法运算放在后台线程，UI只负责展示，防止界面卡顿。

Q13：高级脚本和普通脚本在插入新的输入量时有哪些差异？

 A:

1. 普通脚本（Simple Script）：输入输出变量需要在脚本属性面板手动添加绑定；变量只能是简单类型，不支持复杂对象；只能绑定当前VisionPro工具链里的输出。
2. 高级脚本（Advanced Script）：可以直接在代码里引用CogToolGroup内所有工具对象，不需要手动绑定变量；支持复杂图像、工具对象作为输入；可以直接调用VisionPro工具的属性与方法。
3. 新增输入量：普通脚本必须在界面手动添加输入端口；高级脚本直接在代码读取工具实例，不用手动添加端口。

Q14：在简单脚本中input点不到已有的元素是什么情况？

 A:

1. 变量类型不匹配：简单脚本输入端口只支持基础类型，图像、工具对象无法直接作为输入。
2. 工具执行顺序问题：要读取的工具，执行顺序在脚本工具之后，此时还没有运行输出数据。
3. 命名冲突：变量名重复，或者名称有特殊符号。
4. 缓存未刷新：修改工具链后没有重新保存、运行工具组，变量没有加载。
5. 端口方向错误：混淆输入端口和输出端口。

Q15：知道工作距离知道相机绑定尺寸，焦距，如何确定视野？

 A:

1. 放大倍率M = 靶面尺寸 / 视野尺寸；M ≈ 焦距 / 工作距离（薄透镜近似，工作距离远大于焦距时）。
2. 推导公式：视野 = 靶面尺寸 × 工作距离 / 焦距。
3. 分别计算水平视野、垂直视野，使用相机水平、垂直靶面尺寸代入公式。
4. 注意：远心镜头不能直接套用这个公式，需要使用镜头厂商提供的放大倍率计算视野。
5. 选型预留余量，实际视野要比产品尺寸略大。

Q16：检测细小划痕时，选择镜头需要关注哪些参数？

 A:

1. 放大倍率：足够放大倍率，保证划痕能在图像上占用足够像素。
2. 分辨率：镜头的光学分辨率，要满足检测最小划痕的像素要求。
3. 畸变：优先低畸变镜头；如果尺寸测量，选用远心镜头消除透视畸变。
4. 景深：保证产品表面高低起伏时，划痕都能清晰对焦。
5. 工作距离：满足现场安装空间。
6. 接口：和相机接口匹配。

Q17：要检测一元硬币上面的凸起的“一”时，需要用什么光源？

 A:

1. 使用**低角度环形光源（斜光）**。
2. 原理：低角度光从侧面斜打，凸起文字边缘会产生阴影，强化凸起轮廓和背景对比度。
3. 不推荐同轴光源：垂直打光，凸起表面反光均匀，很难凸显高低落差。
4. 可以搭配试光，调整光源高度与角度，找到阴影效果最好的位置。

## 3组

Q1：wpf你自己在开发过程中用到的技术点 并解释一下

 A:

1. 数据绑定：WPF核心特性，将界面控件属性和后台对象属性关联，数据变化自动同步UI，不用手动操作控件赋值，减少UI代码。
2. MVVM架构：分离View、ViewModel、Model，界面和业务逻辑解耦，方便单元测试，便于界面和逻辑独立修改。
3. 依赖属性（DependencyProperty）：WPF控件属性底层实现，支持绑定、样式、动画、属性继承，区别于普通C#属性。
4. 路由事件：事件可以在可视化树向上冒泡或者向下隧道传递，父容器可以统一处理子控件事件，简化事件代码。
5. 命令（ICommand）：把按钮点击等UI操作封装成命令，放在ViewModel中，实现UI交互逻辑和界面分离，适配MVVM。
6. 资源与样式、模板：Style统一控件外观，ControlTemplate自定义控件结构，资源字典统一管理颜色、样式，方便换肤。
7. 异步+Dispatcher：后台Task做图像算法、数据库操作，通过Dispatcher回到UI线程更新界面，避免UI卡死。
8. ObservableCollection：动态集合，集合增删自动通知界面刷新，代替普通List，用于表格、列表数据展示。

Q2：解释一下MVVM

 A:

1. MVVM是Model-View-ViewModel的缩写，是MVC模式的改进版，核心是把UI界面、业务逻辑、数据层完全解耦。
2. View层：只负责界面展示和接收用户操作，不写任何业务处理逻辑。
3. ViewModel层：作为中间桥梁，封装所有UI相关的状态和业务逻辑，不持有任何View的引用，避免内存泄漏。
4. Model层：负责底层数据获取和基础业务规则处理。
5. 它依托WPF的声明式数据绑定能力，实现数据和界面的自动同步，大幅提升了代码的可测试性和可维护性，是WPF开发的主流架构模式。

Q1：2d检测使用什么样的框架，解决什么问题？

 A:

1. 视觉算法框架：VisionPro、OpenCV、Halcon。VisionPro上手快，工具封装完善，适合快速开发2D定位、尺寸、外观缺陷项目；OpenCV开源灵活，适合自定义图像预处理；Halcon算子丰富，稳定性强。
2. 上位机开发框架：C# Winform或者WPF。Winform开发简单，适合快速交付产线软件；WPF适合界面复杂、需要MVVM架构的项目。

Q2：3d相机除了检测孔洞缺陷还有什么缺陷？

 A:

1. 高度差类缺陷：凸起、凹陷、变形、翘曲、平面度、高度超差。
2. 体积类缺陷：缺料、溢胶、多余物料。
3. 装配类检测：零件有无、装配间隙、引脚共面度。
4. 截面轮廓检测：轮廓形变、折弯角度不合格。
5. 厚度测量：产品厚度是否符合规格。
6. 注意：3D相机对反光强、透明材质、微小低对比度平面划痕检测能力有限，这类场景一般搭配2D视觉。

Q3：一般都用脚本做过什么样的的事？ 

A:

1. 工具组内逻辑控制：判断PMA定位结果是否合格，不合格直接跳过后续检测工具，节约运行时间。
2. 数据计算：读取卡尺、Blob结果，做二次运算，换算物理尺寸，判断是否超出上下限阈值。
3. 变量传递：在多个VisionPro工具之间传递坐标、角度、标记点，动态修改ROI位置。
4. 动态参数修改：根据前面检测结果，动态修改后续工具阈值、搜索范围。
5. 数据组装：收集所有检测结果，拼接成报文，发给上位机或者保存到日志。
6. 异常处理：捕获工具运行异常，标记本次检测NG，记录异常信息。

Q4：什么是栈，什么是堆？

 A:

1. 栈（Stack）：由系统自动分配、自动释放内存。存放值类型变量、引用类型变量的引用地址、函数参数、局部变量。内存分配速度快，空间较小，遵循先进后出。函数执行完成，栈内存自动回收。
2. 堆（Heap）：由开发者手动申请，CLR垃圾回收机制GC负责回收。存放引用类型的实例对象，空间大，分配速度慢。只要对象还有引用指向，GC就不会回收，没有引用时等待GC扫描回收。

Q5：引用类型都有哪些，值类型都有哪些？

 A:

1. 值类型：struct结构体、枚举enum、基础类型int、double、bool、char、byte等，存储在栈中，变量存的是数据本身。
2. 引用类型：class类、string字符串、数组、委托、接口、object。变量保存的是堆里面对象的内存地址，实际对象数据存放在堆内存。

Q6：委托和事件的区别？

 A:

1. 委托：是一种类型安全的函数指针，可以指向一个或者多个方法，保存方法的地址，能够直接调用。
2. 事件：是委托的封装，基于委托实现，对外只提供订阅和取消订阅，不允许外部直接赋值、触发。
3. 访问权限：委托在外部可以直接赋值覆盖；事件只能 +=、-=，外部无法直接调用。
4. 使用场景：委托适合直接传递方法；事件用于类内部触发消息通知，实现解耦，比如上位机接收图像采集完成通知。

Q7：什么是面向对象编程？

 A:

1. 面向对象编程简称OOP，是一种编程思想，把程序看成是多个对象的集合。
2. 将数据（属性）和操作数据的方法封装到类里面，通过实例化类创建对象。
3. 核心思想：把现实事物抽象成类，通过对象交互完成业务功能。
4. 三大特性：封装、继承、多态，提升代码复用性、可维护性，降低耦合。

Q8：分别介绍一下面向对象的封装、继承和多态 

A:

1. 封装：把类的字段、属性、方法打包在一起，使用访问修饰符控制访问权限。隐藏内部实现细节，只对外暴露必要接口，外部不需要关心内部如何实现。
2. 继承：允许一个类（子类）继承另一个类（父类），复用父类已有的属性和方法。子类可以扩展自己新的功能，减少重复代码。C#只支持单继承。
3. 多态：同一个接口，不同对象有不同实现。分为虚方法重写和接口实现。调用同一个方法，根据对象实际类型执行对应的逻辑，便于程序扩展。

## 5组

Q1：做过有挑战的项目,详细介绍

 A:

1. 项目背景：多相机产品外观与尺寸检测上位机，基于C# Winform+VisionPro。产品在载具上随流水线移动，需要多相机同步抓拍，完成定位、尺寸测量、表面缺陷检测，检测结果与PLC交互，节拍要求很高。
2. 难点一：多相机成像不同步，产品位置波动，多个相机检测坐标不统一，缺陷坐标无法映射到同一世界坐标系。
3. 解决：使用九点标定+旋转标定，把每个相机图像坐标统一转换到载具世界坐标系，完成多相机坐标关联。
4. 难点二：产线节拍紧张，图像采集、算法处理、数据库存储、UI刷新串行执行时总耗时超标。
5. 解决：重构为多线程异步框架，图像采集、算法运算、IO通信、数据持久化分离成独立任务；图像保存、数据库写入放到后台队列异步执行，不阻塞算法主线程。
6. 难点三：产品表面反光，微小划痕缺陷对比度低，传统算法容易出现漏检误检。
7. 解决：优化光源方案，增加偏振片抑制反光；结合PMA稳定定位，Blob和灰度差分做缺陷提取，反复迭代阈值，平衡漏检和误检。
8. 难点四：上位机与PLC串口通讯偶发丢包断连。
9. 解决：单独线程处理串口收发，增加心跳、CRC校验、超时重连，处理粘包分包问题。
10. 项目成果：满足客户节拍与精度要求，实现产品全流程数据追溯，稳定交付产线。

Q2：采图和图像处理用的是串行吗 

A:

1. 不会使用串行。如果采图、算法处理、UI刷新串行执行，会造成整体耗时叠加，很容易达不到产线节拍。
2. 采用多线程异步方案：图像采集是独立线程，相机触发抓拍；图像采集完成后触发算法任务，在后台线程执行图像处理。
3. UI只负责展示图像与结果，不参与算法运算。
4. 控制并发：使用信号量控制并发数量，防止多帧图像同时运算造成CPU占用过高。

Q3：九点标定旋转标定过程

 A:

1. 准备标定板：使用带阵列圆点的标定板，固定在载具上。
2. 九点标定：移动标定板到相机视野内9个不同位置，采集图像；VisionPro读取每个点图像坐标，同时记录载具对应的世界物理坐标。
3. 生成仿射变换矩阵，建立图像像素坐标到世界坐标的映射，完成像素与物理尺寸转换。
4. 旋转标定：将标定板旋转多个角度，采集多组旋转后的标定点。
5. 计算载具旋转带来的坐标偏移，修正旋转角度带来的坐标偏差。
6. 最终得到完整坐标转换模型，物体旋转后，图像上的点依然可以准确换算到载具世界坐标系，多用于多相机统一坐标。

Q4：如何更新图像显示 会用委托吗 跨线程处理用委托要注意什么 

A:

1. 更新图像显示：后台线程采集、处理图像完成后，使用委托把图像对象传递到UI线程，刷新界面图像控件。
2. 会使用委托，WPF/Winform都不允许跨线程直接操作UI控件。
3. 跨线程委托注意事项：
   1. 判断控件的InvokeRequired，true则使用Invoke/BeginInvoke委托回UI线程更新界面。
   2. Invoke是同步阻塞，BeginInvoke是异步，大量图像刷新优先用BeginInvoke，避免阻塞后台算法线程。
   3. 注意内存，不要频繁创建图像对象，复用图像缓存，防止内存泄漏。
   4. 窗体关闭时，停止后台任务，取消未执行的委托回调，防止窗体销毁后还执行UI操作，引发程序崩溃。
   5. 委托传递的图像数据尽量做拷贝，防止后台线程和UI线程同时读写同一张图像。

Q5：委托和事件有什么区别 

A:

1. 委托：是类型安全的方法指针，可以指向一个或多个方法；外部可以直接赋值覆盖，也可以直接调用委托。
2. 事件：是委托的封装，只能在类内部触发；外部只能用+=订阅、-=取消订阅，不能直接赋值覆盖，也不能在类外部直接触发。
3. 安全性：事件防止外部随意覆盖回调函数，更适合做消息通知。
4. 使用场景：委托适合直接传递方法；事件用于模块间解耦通知，例如图像采集完成事件。

Q6：介绍多相机坐标统一 

A:

1. 核心目标：把多个相机各自的图像像素坐标，全部转换到同一个世界坐标系（一般以载具/工装作为世界基准）。
2. 单相机九点标定：每个相机单独做九点标定，建立各自图像坐标到世界坐标的仿射矩阵。
3. 基准统一：使用同一块标定板，所有相机拍摄同一标定板，保证所有相机共用一套世界坐标基准。
4. 旋转补偿：载具存在旋转时，增加旋转标定，修正旋转带来的坐标偏移。
5. 坐标转换流程：相机A检测得到缺陷像素点 → 通过A相机标定矩阵转为世界坐标 → 该世界坐标可直接映射到相机B视野对应的位置。
6. 应用场景：产品跨多个相机视野，缺陷位置可以在全局坐标系下统一输出给PLC。

Q7：做过运控吗 具体干了什么 

A:

1. 做过运控相关上位机开发，主要是视觉和运动控制设备交互。
2. 工作内容：
   1. 上位机通过TCP/串口和运动控制器通讯，下发点位、运动指令。
   2. 视觉算法算出产品偏移量，将XY偏移、角度补偿值发送给运动控制器，引导载具做位置纠偏。
   3. 读取运动控制器状态，判断运动到位信号，到位后触发相机拍照。
